# dsh-zen PRD（产品需求）

下游：[SRS](SRS.md) · [架构设计](ARCHITECTURE.md) · [预研](RESEARCH.md)

## 1. 背景

用纯文本管理 agent 的项目工作——一份 Markdown 计划、一张任务表、状态写在表格单元格里——在单个 agent 时够用，在多 agent 时失效。失效不是因为它“不好看”，而是两条随规模放大的乘积。

## 2. 成本模型

| | 文档式管理 | 目标形态 |
|---|---|---|
| 读 | 每个 agent 每次读**整份**文档：N × len | 各取所需切片：≈ Σ 各自所需 |
| 写 | 改一个字段 = 整篇重写，冲突面 = 整篇 | 一条记录一次写，冲突面 = 那个字段 |
| 新 agent 加入 | 再读一遍整份才知道现状 | 一条就绪查询 |
| 定位“谁在做什么” | 全文检索 + 人读 | 一条视图 |

读整份还会挤占上下文窗口导致判断质量下降——这比 token 更贵。

推论：核心不是“把文档搬进数据库”，而是**最小读写单元**。读要能按需切片，写要能定点落在一条记录上。

## 3. 定位

**对标 Jira / 禅道一类项目管理系统**，把“主用户是 agent”作为重新取舍的前提。判断标准不是功能多少，而是**每个机制省下的成本是否大于它自身的成本**。

这是**效率工具，不是安全工具**：机制的第一问题是“它省了什么”，不是“它防住了什么”。防的是误操作与幻觉，不是刻意绕过；配置改动在 git diff 里可见，这就是那层保护。

交付形态是 **DSH 插件**：模型通过插件注册的内置工具使用它，不经过 skill，也不需要自己拼命令行。人可以看，但很少主动看。所以能力宽度不受限——多一个字段、多一个类型，不消耗任何人；付账的是 agent 的上下文。

## 4. 用户与场景

主用户是 agent（含 subagent），次用户是监督的人。按频率：

1. 会话启动：我该做什么 → 就绪查询
2. 开工：占用任务 → 状态流转
3. 执行中发现新工作 → 提任务
4. 完成：留产物、勾验收 → 交回队列
5. 人偶尔看：终端的看板或统计

## 5. 与对标产品的关系

| 能力域 | Jira / 禅道 | 本产品 | 处置 |
|---|---|---|---|
| 容器层级 | 产品 / 项目 / 执行 | 仓库 = 项目 | 取（收窄） |
| 工作项类型 | Issue Type + Scheme | 类型可配置 | 取 |
| 字段体系 | 自定义字段 + 配置方案 | 类型 → 字段方案 | 取 |
| 工作流 | 状态、转换、条件、校验、动作 | 转换 + 守卫 + 效果 | 取（压成两段） |
| 迭代与版本 | Sprint / Version / Epic | 无 | **弃** |
| 关联 | blocks / relates / duplicates / clones | 三类 | 取 |
| 检索 | JQL | 预设视图 + 字段过滤 | **改** |
| 权限 | 权限方案 + 角色 | 能力角色 + 授予表 | **削** |
| 审计 | Change History | 追加式事件 | 取 |
| 协作 | 评论、附件、关注者 | 评论 + 产物引用 | 改 |
| 报表 | 燃尽、累积流 | 结构化统计，不画图 | 改 |
| 表单 / 通知 / 二进制附件 | 不适用 | 无 | 弃 |

弃掉的四项是“agent 主用户”推到底的结果，不是能力缺失。

## 6. 核心设计理念

**分工是三件事，不是一张权限表**：角色（干哪类活）、关注域（默认看到什么）、统筹（谁拆任务、谁处理卡住的）。

**没有工期**。agent 不按时间跟踪，时间只用于过期与清理（租约 TTL、stale 检测、review 周期），不进排期与进度。

**进度是拓扑的**：就绪多少、阻塞多少、卡在谁那里，不是“还剩几天”。

**计划只是容器**：分类标签 + 上下文，没有生命周期，进度由任务计数派生。

## 7. 能力域清单

容器与归属 · 类型与字段方案 · 状态与转移 · 关联 · 视图与检索 · 并发与租约 · 最小读写单元 · 结构化报告与派生阶段 · 审计 · 角色与权限 · 快照与迁移 · 人视图。

逐条要求见 [SRS](SRS.md) §6。

## 8. 非目标

无自有 Web 服务与独立前端应用（看板面板寄生在 DSH 宿主的路由里，不另起端口与进程）、无多租户、无跨机并发同步、无查询语言、无守护进程、无审批流、不做日历与工期。

## 9. 成功判据

1. 新克隆的仓库能在一条命令内恢复工作视图，agent 不需要读任何 Markdown 计划。
2. 五个 agent 并行工作时，同一任务不会被两人同时做，且无人因等待而空转。
3. 一次典型会话启动读到的内容可计量，且远小于“读完所有计划文档”。
4. 人不需要打开任何工具就能判断“现在卡在哪”。
5. 任务的历史可完整重建，包括谁在什么角色下改了什么。

## 10. 产品裁定

以下 20 条为产品级裁定，实现不得违背。

| # | 裁定 |
|---|---|
| 1 | 效率工具，非安全工具 |
| 2 | 一个项目一个库 |
| 3 | 项目 = 仓库闭包，ID 前缀固定，不做跨项目 |
| 4 | 统筹拆一次，就绪队列自取，不逐条派工 |
| 5 | 默认三态流转；review 定期批处理，不是流程节点 |
| 6 | 计划外发现直接提任务，不设授权闸门 |
| 7 | 不设授权链（无 Mandate / strength / 放权档位），只有角色 |
| 8 | 任务按来源落位：带计划进计划，否则进积压 |
| 9 | 预设视图 + 字段过滤，不做查询语言 |
| 10 | 无工期；时间只用于过期与清理 |
| 11 | 优先级只有 planner / lead 能改 |
| 12 | planner 拆任务时消费积压，顺带并单去重 |
| 13 | 产物四类；验收逐条勾选 |
| 14 | 无独立认领命令，进入 wip 即占用 |
| 15 | 依赖阻塞与主动受阻分离；受阻释放租约 |
| 16 | 无归档机制；终态只读替代 |
| 17 | 计划无状态机，纯容器 |
| 18 | 权限矩阵：验收内容与勾选分离授权；`blocks` 收口；`todo→wip` 全开 |
| 19 | 角色每命令声明 + 授予表校验，缺省 implementer |
| 20 | 同机多进程共享库；跨机只做快照迁移 |
